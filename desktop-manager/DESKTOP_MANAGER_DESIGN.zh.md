# DSH 桌面实例管理器 设计方案

状态：完整功能已实施并通过单元、真实 Electron 与打包应用验证。Apple Developer ID 签名、公证和管理器自身更新源属于外部发布基础设施。

## 1. 目标

做一个 macOS 桌面应用，用于管理多个 DSH（DeepSeek Harness）运行版本。

应用提供三件事：打开不同版本 DSH 实例的入口、并行运行多个实例的能力、以及版本切换与回退的控制台。

应用同时是版本管理器：内置一个已验证的官方 DSH 作为兜底运行版本，可以下载并校验更新的官方版本，也可以注册本机任意 DSH 源码目录作为本地运行版本。

应用自身不依赖任何被管理的 DSH 版本。某个 DSH 完全无法启动时，桌面应用仍然可用，仍然可以启动另一个版本去修复它。

桌面管理器沿用 DSH Web 的产品语言：中文文案、左侧导航、白色中心工作面与可选右侧详情栏；近黑用于主操作，DeepSeek 蓝用于选中与进行中状态。

## 2. 目录规划

目标目录结构：

```text
/Users/liangyc/Documents/Deepseek-Harness/
├── desktop-manager/   # 本桌面管理器
├── dsh-v1/            # 当前本地运行版本
├── <其他-runtime>/    # 用户按需注册的任意本地运行版本
└── .../               # 更多本地版本

<应用 bundle>/Contents/Resources/runtimes/official/bundled/   # 内置官方 DSH，只读，随应用签名分发
<应用数据目录>/
├── runtimes/official/downloaded/<version>/   # 已下载官方 DSH，只读
├── worktrees/<runtime-id>/        # 管理器创建的 Git worktree
├── environments/<environment-id>/ # 独立或克隆 DSH_HOME
├── backups/<backup-id>/           # 环境备份、清单与收据
├── logs/instances|tasks/          # 实例与任务日志
└── manager-state.json             # version 3 原子状态
```

应用数据目录位于 macOS Application Support，路径示例为 `~/Library/Application Support/DSH Manager/`。应用数据目录存放下载的官方版本、环境、实例状态、日志与锁，不存放内置官方版本；内置官方版本位于应用 bundle 内（见第 2 节目录结构）。应用数据绝不存放在被管理的运行版本目录内，保证运行版本全部损坏时管理器仍可启动。

`/Users/liangyc/Documents/dsh` 到目标结构的迁移见第 11 节。

## 3. 核心概念

四个概念相互独立，必须分开选择。

运行版本（Runtime）：DSH 代码本体，即某个文件夹里的 dsh 源码或构建产物。来源分为内置官方、已下载官方、本地文件夹三类，见第 6 节。

工作区（Workspace）：用户在 DSH 新建会话时选择的项目目录，是该会话中 Agent 读取和修改文件的主要范围。它不属于管理器实例配置。

环境（Environment）：该实例的数据根目录，即 DSH_HOME。存放设置、凭据、Profile、会话、附件。环境分为生产、独立、克隆三类，见第 8 节。

实例（Instance）：一个可运行的 DSH 服务，由一个运行版本和一个环境组合而成。管理器为它创建独立的内部启动目录，并在每次启动时自动分配端口；内部目录只满足进程 `cwd` 要求，不代表用户项目。一个运行版本可以同时有多个实例，也可以只有零个。

运行版本与会话工作区保持独立。稳定 runtime 启动后，用户可以在 DSH 中为每个新会话选择任意项目目录；候选 runtime 同时以自动端口和隔离环境启动测试实例。候选版本完全无法启动时，稳定实例仍不受影响。

## 4. 功能范围

实例管理：创建、启动、停止、重启、删除实例；为实例打开 GUI；查看启动与运行日志；查看实例状态与端口。

运行版本管理：注册本地运行版本；查看运行版本信息与预检结果；管理内置与已下载官方版本；标记默认运行版本；删除已注册的运行版本。

官方版本更新：从 npm 拉取最新官方版本信息；下载、校验、注册为新的官方运行版本；不覆盖内置兜底版本；不自动改变默认运行版本。

环境管理：每个实例默认使用独立 DSH_HOME；可以创建空环境、注册生产环境，或从现有环境克隆完整副本。不同版本使用各自副本即可并行运行，克隆后产生的会话历史独立演化且不自动合并。管理器禁止自己监督的两个运行实例并发写同一规范化环境路径。

切换与回退：把实例提升为新的生产默认版本；在提升失败时同时回退运行版本与环境数据。

预检与构建：注册运行版本时执行预检；提供构建、类型检查、测试入口；构建失败阻止启动。

## 5. 页面设计

应用采用与 DSH Web 一致的三栏工作台：左侧导航、中心工作面、可选右侧详情栏。主面为白色，侧栏使用近白背景；近黑胶囊按钮承担主操作，DeepSeek 蓝只用于选中、进行中与业务强调，绿色只表示明确成功。

左侧栏固定包含品牌、新建实例、概览、运行时、实例列表与底部设置入口。实例以状态点、名称和中文状态显示，不再使用顶部浏览器标签。中心区在概览、运行时预检和实例 Web GUI 之间切换；右侧详情栏用于日志，不覆盖中心工作流。

产品文案使用中文，动作短而直接，例如“新建实例”“注册运行时”“创建环境”“重新预检”“查看日志”。内部枚举必须映射为“启动中”“运行中”“停止中”“已停止”“失败”，不直接暴露英文状态。

### 5.1 概览

概览是默认工作面，不做欢迎页。顶部只显示页面标题、运行实例与环境数量摘要，以及“新建实例”主操作。下方按顺序展示实例列表、运行时和环境；普通区域不套装饰卡片，主要依靠白色表面、极淡边界和 hover 背景建立层级。

实例行显示实例名、运行时、环境、实际端口与状态，并提供启动、停止、强制停止、重新启动和日志操作。运行时显示版本与预检状态；环境显示独立、克隆或生产类型及当前占用者。

### 5.2 新建实例与环境

侧栏和概览均可打开新建实例对话框。用户只需填写名称、运行时和环境；管理器创建独立内部启动目录，端口每次通过 `0` 由操作系统原子分配。项目工作区在 DSH 新建会话时选择，不在启动器中重复配置。

环境可以新建空 DSH_HOME、注册现有生产环境，或从现有环境克隆。克隆需要选择来源环境与目标运行时。运行中的受管来源实例先优雅停止，复制完成后立即重新启动，避免在线冻结留下不可恢复的进程组。

对话框沿用 DSH 的 24px 圆角、弱遮罩、系统中文字体、36px 胶囊按钮和 8px 输入框圆角。说明只保留当前动作与直接后果，不显示开发者式功能介绍。

### 5.3 实例工作面

实例工作面由 58px 工具栏与嵌入的 DSH Web GUI 构成。工具栏显示实例、运行时、环境和实际端口，并提供日志、外部浏览器、重新启动与停止操作。

嵌入视图按实例使用独立 Electron partition。自动端口变化时销毁旧 origin 绑定并重建视图；切离实例时取消尚未完成的异步展示，旧 load 不得覆盖概览或另一个实例。加载错误必须反馈到宿主错误栏，不显示无诊断空白。

### 5.4 日志详情

日志在右侧 360px 详情栏中展示，使用与 DSH details 列相同的浅色表面与弱边界。内容读取每个实例的持久化 stdout/stderr 文件；实例从未启动时显示“暂无日志输出”，而不是报文件不存在。

### 5.5 运行时与设置

运行时工作面列出路径、版本、Git 状态和全部预检项，支持本地源码 checkout 与已发布 `@deepseek-ai/dsh` 包布局。固定文案和修复建议使用中文，路径、版本与底层原始错误保持原值。

设置入口位于侧栏底部，采用 DSH 同款两列设置面板，可选择实例在内嵌视图或外部浏览器中打开，并控制启动时官方更新检查。中文原生应用菜单提供新建实例、概览、运行时、设置、编辑和窗口命令；默认运行时、数据位置及日志路径在对应管理工作面直接显示。

## 6. 运行版本

### 6.1 内置官方版本

应用安装时内置一份已验证的官方 DSH 完整 npm 消费者依赖闭包，存放于应用 bundle 内 `Contents/Resources/runtimes/official/bundled/current/`，只读。打包脚本生成 package-lock、根包 integrity、安装收据、SHA-256 文件清单与 READY 提交标记。

内置版本自包含完整的已安装、已构建 DSH 依赖闭包，并通过 Electron 自带 Node 启动，不依赖系统 Node 或 pnpm。

内置版本保证离线或网络故障时仍有一个可运行的官方版本。下载新官方版本不会覆盖内置版本。

### 6.2 已下载官方版本

应用从固定 npm registry 查询 `@deepseek-ai/dsh` 最新版本。用户确认后，安装器在隔离临时 HOME、cache 与 userconfig 中通过固定 npm CLI 安装精确版本及完整消费者依赖闭包，校验后原子发布到应用数据目录 `runtimes/official/downloaded/<version>/`，注册为只读官方运行版本。

校验按以下信任边界执行：
- registry 固定为 `https://registry.npmjs.org`，拒绝重定向和跨 origin tarball；
- 强制校验 npm 元数据中的 sha512 `dist.integrity`；
- 校验 package-lock 根包名称、版本和 integrity 等于期望值；
- 校验 CLI 身份、完整运行时预检、一次性 DSH_HOME Web readiness/HTTP 探针和发布前 SHA-256 文件清单；
- 写入安装收据和 READY 后才通过原子目录 rename 发布。

校验失败则丢弃下载结果，不注册。下载行为可被用户取消。

多个已下载版本可共存。删除已下载版本需要确认；被运行中实例使用的版本禁止删除。

### 6.3 本地运行版本

用户注册本机任意目录作为本地运行版本，例如 `/Users/liangyc/Documents/Deepseek-Harness/dsh-v1`。

注册时记录：路径、名称、注册时间、Git 远端、当前 commit、工作树是否干净、Node 与 pnpm 版本、依赖是否安装、构建产物是否存在。

工作树脏的目录可以注册，但被标记为稳定版本或用于生产提升的目录应指向已提交 commit，保证回退目标明确。

### 6.4 预检

预检在注册时执行，在每次启动前重跑。预检项：

- 目录存在且是 DSH 源码或封装后的完整运行产物。
- 本地源码根 manifest 声明的 Node 与 pnpm 工具链可用。
- `node_modules` 已安装，缺失时提示先执行依赖安装。
- 完整构建产物存在：至少包含 `apps/cli/lib/bin.js`、依赖包 `lib` 与 `apps/web/dist/index.html`；单独存在 CLI 文件不代表可启动。
- 目录位于 Git 仓库时，按该 runtime 子目录范围记录 commit 与工作树状态。
- 官方安装额外执行隔离的一次性 DSH_HOME Web readiness/HTTP 探针并生成构建文件 fingerprint；本地源码仍以每次实际 spawn、readiness 与 HTTP 确认为最终结果。

预检结果为通过、警告、失败三级。失败项列出具体原因与修正动作。预检通过才能启动实例。

### 6.5 启动命令

本地运行版本启动已构建实例的命令：

```text
node <runtime>/apps/cli/lib/bin.js web --host 127.0.0.1 --port <port-or-0> --no-open
```

内置官方版本使用其自带的 Node 运行时与完整依赖闭包，通过 bundle 内入口启动，不依赖系统 Node 与 pnpm。本地运行版本使用系统 Node/pnpm，启动前按第 6.4 节预检其声明的工具链。

工作目录设为实例的工作目录。环境变量 DSH_HOME 设为实例的环境目录。以完整构建产物启动，不重新构建。端口默认传 `0` 让操作系统原子分配；管理器解析完整 Loader settle 后输出的 `dsh web: http://127.0.0.1:<port>` readiness 行，再执行一次 HTTP 确认并持久化实际端口。用户手工指定端口时，最终仍以 DSH 的 bind 结果为准。

修改过源码的运行版本需要先构建再启动。管理器提供构建入口，构建成功后才能启动。构建失败时禁止启动并展示错误。

## 7. 实例生命周期

启动：检查预检结果；检查环境未被其他受管实例占用；分配日志文件；以回环 host 和自动或指定端口启动进程；解析 DSH readiness 输出并执行 HTTP 确认。

就绪检查：以 `dsh web:` 输出为服务组合完成的权威信号，不能把端口已 bind 或启动中间态的 HTTP 404 当作就绪。超时或提前退出均标记失败并保留日志。

停止：管理器先发送一次 SIGTERM，并等待整个 detached 进程组消失，而不是只等待 leader 退出。当前 DSH 自身执行优雅 teardown；六秒后进程组仍存活时，用户可显式强制停止，退出流程则发送 SIGKILL 并再次确认组内无后代。状态写盘失败不得阻止发送安全信号。

重启：先停止，再按启动流程重新启动。

删除：先停止实例，再删除实例元数据。隔离环境由用户选择是否同时删除；生产环境永不自动删除。

异常退出：进程非预期退出时，管理器清理同组后代并标记异常，不自动重启。若管理器自身崩溃或被 SIGKILL，上次处于活动状态的实例在下次启动进入隔离；管理器保留 PID、端口和日志线索，禁止直接启动。用户明确确认旧进程已停止并选择自动或固定端口后，管理器同时探测旧进程组和端口，只有均已释放才解除隔离。

macOS 关闭管理器窗口只隐藏界面，Electron 主进程继续监督运行中实例；从菜单真正退出应用时停止全部受管进程组。Windows/Linux 关闭最后窗口时受控退出。管理器不冒险接管崩溃后可能存在的孤儿进程：仅凭 PID 会遇到复用、日志句柄和端口归属问题，因此持久化 PID、端口、日志和操作阶段并进入隔离，要求用户确认进程组与端口均已释放。

## 8. 环境与数据

DSH_HOME 由管理器通过环境变量注入，用于隔离 DSH 的设置、凭据、Profile、会话与附件；它不是 Agent 文件访问沙箱，实例仍会按工具策略读写 Workspace 和其他获准路径。

生产环境：默认可注册 `~/.dsh`，与现有使用保持一致。同一时刻只有一个受管实例可以使用同一规范化生产环境路径。

隔离环境：位于 `<应用数据目录>/environments/<environment-id>/home/`，不同实例默认使用不同环境，互不共享。

克隆环境：从指定来源 DSH_HOME 复制完整环境，不只复制 `sessions/`。同卷 APFS 优先使用 copy-on-write；克隆完成后删除 `profiles/node_modules` 中指向来源 runtime 的依赖 fallback，由目标 runtime 首次启动时重建。克隆记录来源环境、来源实例、来源 runtime/commit、时间与复制方法，此后双方独立演化且不自动合并。

运行中来源的克隆：管理器先优雅停止自己监督的源实例，确认进程组退出后执行 APFS copy-on-write 或普通复制，随后立即重新启动源实例。管理器崩溃不会留下被 SIGSTOP 永久冻结的来源进程；停止失败时拒绝开始复制。

并发规则：不同版本只要使用不同环境副本即可同时运行。管理器禁止两个受管运行实例使用 realpath 相同的 DSH_HOME；相同 Workspace 可以并行，但界面提示两个 Agent 同时修改文件的冲突风险。

数据安全：管理器自身不解析会话格式，不做会话合并或事件级迁移。复制、提升与回退以完整环境目录为单位。

管理器元数据使用 version 3 状态格式，覆盖设置、运行时、环境、实例、任务、备份、提升、模板和长操作资源锁。提交顺序为同目录临时文件写入与 `fsync`、上一 primary 的备份临时文件写入与 `fsync`、原子替换 `.bak`、目录 `fsync`、原子替换 primary、再次目录 `fsync`；内存状态只在该流程成功且完整严格解码通过后发布。损坏 primary 从上一有效备份恢复并隔离原文件；未来格式版本拒绝降级读取。version 1/2 自动迁移，无法确定来源的非零端口必须由用户重新确认模式。受管 runtime/worktree/environment 删除在首次 rename 前写入包含原路径、暂存路径和资源键的持久 operation journal，元数据删除与 `metadata-removed` 阶段同一次状态提交，清理后才进入 committed；启动对账同时处理进程崩溃和 `.bak` 复活旧元数据。环境 restore 使用 `staged-ready`、`diagnostic-moved`、`restored` 三阶段 swap journal，canonical 缺失时可幂等完成或恢复。

## 9. 默认版本、提升与回退

默认版本是新建实例的预选运行版本，不自动切换运行中实例，不自动替换生产环境。

提升流程：候选实例在隔离端口与隔离环境中完成构建、启动、就绪检查，并由用户实际发起一次测试对话；本地候选必须保持测试时的干净 commit 与完整依赖闭包指纹，再复制为管理器私有、不可构建的 production snapshot 并复核身份；停止生产实例；备份生产环境；紧邻 spawn 重新验证目标身份。启动先持久化 launch intent，macOS detached process group 在一次性随机 gate 后等待，PID 状态提交成功才允许 exec DSH。确认启动与对话正常后把 snapshot 记录为新的默认版本，并保留上一运行版本与备份。任何恢复失败都保持 recovery-required 隔离，普通 PID/端口恢复不能解除。

回退流程：停止故障实例；把故障后的环境目录移到诊断目录；恢复备份的生产环境；用上一运行版本启动生产实例；确认恢复正常。回退同时恢复运行版本与环境，因为仅回退代码可能遇到新版已升级的数据格式。

提升与回退的记录写入应用数据目录，包含时间、运行版本、commit、环境备份路径、结果。

## 10. 技术方案

桌面框架选用 Electron。DSH 与桌面应用同为 TypeScript 与 Node.js 生态，主进程可直接使用 child_process 管理 DSH 子进程，读取 Git、Node、pnpm、端口状态。嵌入式多实例 Web GUI 用 Electron WebContents 承载。Tauri 更轻但需维护 Rust 进程管理层，作为后续评估项。

主进程：运行版本注册与预检、实例进程管理、端口分配、环境占用校验、官方版本下载校验、日志写入、设置持久化。

预加载脚本：通过 contextBridge 暴露窄 IPC 接口。接口只包含管理器功能所需命令：实例列表、启动停止重启、日志读取、运行版本注册、预检、官方版本操作、设置读写。不允许 DSH 页面调用任意进程能力。

渲染进程：React 实现第 5 节页面。

WebContents 安全配置：nodeIntegration 关闭，contextIsolation 开启；限制页面只能导航到 127.0.0.1 的受管端口；实例页面与管理器 IPC 隔离；不向 DSH 页面注入 Node 能力。DSH 自身只绑定回环地址，管理器不自动开放 LAN 端口。

凭据策略：DEEPSEEK_API_KEY 与 provider 凭据由用户放入环境（环境变量或 DSH_HOME 内文件），管理器不读取、不存储、不展示凭据值。官方安装使用固定 registry、独立临时 HOME/cache/userconfig，删除 npm token、auth、proxy 与 Node 注入环境，并以 `--ignore-scripts` 禁止 lifecycle 代码；lockfile 除根条目外的每个包都必须具有固定 HTTPS registry URL 与 sha512 integrity。receipt 强制绑定 schema、source、registry、platform 和当前架构；发现、复用、碰撞发布与每次启动都重新核对 receipt、READY、完整文件清单及实际文件。

## 13. 非目标

## 14. 已确定行为
