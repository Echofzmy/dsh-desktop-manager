# Agent Note: Expected tool outcomes are not execution faults

Status: implemented

English | [中文](2026-08-26-expected-tool-outcomes-not-execution-faults.zh.md)

## Problem

Several defects shared one root: expected tool outcomes were handled as harness execution faults. A tool result that is the contract speaking — schema-argument rejection, an approval-policy block, a human rejection, a sandbox denial, a redundant escalation field, a permission-partial search, a goal update carrying fields its action does not own — is a normal, retryable outcome, not evidence that the harness or the loop broke. Failure classes were read from the English `message` text, so wording changes and localization broke classification; a strict-filling model populating optional keys with the standing sandbox mode raised an approval prompt the call never asked for; broad globs surfaced every `node_modules` file or let unreadable paths look absent; goal updates failed on fractional revisions and on mis-filled conditional fields with generic messages; the deterministic `'never'` approval policy was not distinguished from a human rejection; and settled calls had one undifferentiated failure presentation, so policy blocks and cancellations rendered like real errors.

## Decision

**Settled tool outcomes are one of four kinds, classified from stable codes; only `error` renders as a failure.** The client-runtime classifier defines `ToolOutcomeKind = 'success' | 'stopped' | 'blocked' | 'error'`: `success` when the call is not an error; `stopped` for cancellation or interruption codes (`ABORTED`, `TOOL_NOT_STARTED`, `ASK_CANCELLED`, `TOOL_APPROVAL_CANCELLED`, `SANDBOX_ESCALATION_CANCELLED`, `interrupted`, …); `blocked` for refusals and model-correctable conditions (`TOOL_POLICY_DENIED`, `TOOL_APPROVAL_BLOCKED`/`REJECTED`/`UNAVAILABLE`, `TOOL_POST_BLOCKED`, `SANDBOX_ESCALATION_BLOCKED`/`REJECTED`/`UNAVAILABLE`, `INVALID_ARGS`, `UNKNOWN_TOOL`, the named `FS_*`/`SEARCH_*` conditions, and the `GOAL_TOOL_*` family); `error` for every unknown or uncoded failure. The classifier reads only `isError` and `error.code` — never the model-facing text. The trajectory and tool rows apply the kind to presentation: only `error` carries the failure state (`data-error`), while `stopped` and `blocked` render non-red under the row-state vocabulary `running | ok | error | stopped | blocked`. The generic tool-row model, its keyed per-tool views (bash, read, search, todo, web, ask-question, file-mutation), and the skill rows all derive their state through the same `toolOutcomeKind` classifier. In the trajectory, a user or parent stop of an assistant request — an interrupted message, or an aborted turn with no visible result — settles as `stopped`, never a failure, while a retry or a non-abort boundary keeps `error`, so real provider failures are never downgraded. A blocked row's collapsed denial summary drops the registry's `Error: ` envelope; this is display-only — the durable result text is untouched, and an `error` row keeps the envelope because the message is the failure.

**Recognized expected-failure codes carry `TOOL_`/`SANDBOX_` prefixes.** The shared vocabulary, surfaced as `error.info.code` on the `isError` result: `TOOL_POLICY_DENIED` (a pre-execute policy or guard denial without a more specific code), `TOOL_APPROVAL_BLOCKED`/`REJECTED`/`CANCELLED`/`UNAVAILABLE` (approval-seam outcomes), `TOOL_POST_BLOCKED` (a post-execute `block` decision), and `SANDBOX_ESCALATION_BLOCKED`/`REJECTED`/`CANCELLED`/`UNAVAILABLE` (escalation resolution). `INVALID_ARGS` is shared: schema-argument rejection and escalation argument pairing — `sandbox_permissions` and `justification` travel together and the justification must be non-empty — both throw it, so the client classifies an unpaired escalation field as a correctable `blocked` call. A failure without a code stays `error`; it is never silently downgraded.

**Approval-policy outcomes stay distinct from human rejections.** The closed outcome vocabulary `'allowed-once' | 'rejected' | 'blocked' | 'cancelled' | 'unavailable'` is shared structurally between the [approval seam](../feature/2026-07-06-approval-seam.md) and the sandbox escalation module. `'blocked'` is the deterministic policy outcome — the `'never'` policy resolves every ask at dispatch, before any answerer sees it — and is distinct from a human or answerer `'rejected'`. The denial codes keep the split (`TOOL_APPROVAL_BLOCKED` vs `TOOL_APPROVAL_REJECTED`, `SANDBOX_ESCALATION_BLOCKED` vs `SANDBOX_ESCALATION_REJECTED`), so a policy block and a user refusal never conflate.

**Redundant sandbox requests are not approval prompts; real escalation is enforced at execution; per-agent schemas do not advertise what the agent cannot get.** A `sandbox_permissions` request that is not strictly wider than the call's effective mode is a strict-schema redundant field: the call runs under the effective mode with no approval and no error. Strict widening is an execution check against the per-call effective mode (session override or composition default) through the `WIDER_MODES` ladder — deliberately not a schema constraint, because schemas are registry-global while the effective mode is per-call truth. Per-agent projection (`projectSchema`, applied through `schemasFor(agent)` for prompt assembly and the Code Mode SDK) drives the same predicate as the same-turn denial hint: an agent whose effective approval policy is `'never'`, or whose effective mode is already `danger-full-access`, sees no escalation fields and no escalation description clause — there is nothing to escalate to. The static parameters stay composition-wide for diagnostics and `schemas(scope)`. Execution-time enforcement is unchanged: schema omission is advertising, not a bypass guard.

**Glob discovery bounds scale by default and labels partial results.** `globExcludeNodeModules` is a config key defaulting to `true`: `node_modules` joins the VCS metadata stores in `GLOB_DEFAULT_EXCLUDES`, applied as two negated ripgrep globs per name. A deployment that must inspect dependency sources sets it to `false`, and the tool description and guidance then stop advertising the exclusion (`node_modules` is searched like any other directory) — a deployment never advertises an exclusion it does not apply. A permission-restricted run that could not read some paths returns the found paths with an explicit `warnings` array and appends the partial basis to the model-facing text, so the model never mistakes unreadable paths for absence; over-cap pages follow the [sampling decision](../bug-fix/2026-07-27-glob-sampling.md).

**The goal-update contract keeps the flat discriminant.** `update_goal` retains the flat `action` enum with per-action optional fields enforced in `execute`, rejecting mis-fills with precise omit-style errors (`omit "<field>" when action is "<action>": "<field>" is valid only with action "<owner>"`, code `GOAL_TOOL_INVALID_UPDATE`). `revision` is schema-pinned to `integer`, so a fractional revision fails at the schema level (`INVALID_ARGS`) before any authority check, while empty-string and zero fillers in fields unused by the action still count as omitted. The [model-facing goal tools note](../feature/2026-07-19-model-facing-goal-tools.md) owns the authority split; this note owns the parameter contract.

**Repeated identical failures are advisory, and a failed retry reminds on the second attempt.** The per-agent repeat-call guard enriches the post-execute decision with a model-visible reminder (`additionalContexts` notice) and never vetoes or rewrites calls; a user interjection resets the chain. Its failure-aware tier fires when the previous identical result failed and the run reaches `failureRetryThreshold` (default 2) — the second attempt after a failure — quoting the structured `previous_error_code`, again the stable code rather than parsed message text.

## Alternatives considered

- **Root `oneOf` on tool parameters.** Rejected: the parameter DSL compiles every tool root to an implicit object property map, so a root `oneOf` requires extending the tools API, and strict providers require an object-rooted parameters schema on the wire.
- **One tool per goal action.** Rejected: per-action tools would fragment the shared compare-and-set ref (`goal_id`/`revision`), multiply the shipped roster and its guidance, and churn the tool-list and replay gates.
- **Classify failures by parsing the English message.** Rejected: wording- and localization-fragile; the classifier keys off `error.code` and degrades unknown or uncoded failures to `error` instead.
- **Schema-level widening constraint for escalation.** Rejected: schemas are registry-global and the effective mode is per-call truth; the execution check keeps the closed target enum while judging each call, and per-agent schema projection only shapes advertising.
- **Reject redundant escalation fields.** Rejected: a strict-filling model may legitimately populate the optional keys with the standing mode; that must be a no-op, never a failing call or an approval prompt.
- **Remove escalation from the static parameters entirely.** Rejected: the composition-wide advertisement stays for diagnostics and `schemas(scope)`; per-agent `projectSchema` hides it where it cannot be granted.
- **Repeat-reminder vetoes or blocks repetition.** Rejected: advisory keeps the model in control — the reminder is context, not enforcement, and a blocked call still receives the nudge through `additionalContexts`.

## Consequences

The failure surface is now code-routable: loops, guards, UI, and tests classify outcomes into `success`/`stopped`/`blocked`/`error` without parsing prose, and an unknown failure stays `error` instead of being silently downgraded. UI shows only real failures as errors; policy blocks and cancellations render non-red. Strict-filling models are not punished — redundant optional fields (the standing sandbox mode, empty goal fillers) are harmless no-ops, and users are never prompted for non-events: only a genuinely wider sandbox request raises an approval, enforced at execution. Per-agent schema projection keeps an unavailable escalation out of the model's view without weakening enforcement. The trade-offs: schema-level exclusivity is given up (per-action requiredness for `update_goal` and conditional widening live in each tool's execution path with precise errors, because the enforced JSON Schema subset cannot express if/then or dependent-required), the `node_modules` exclusion is a config default rather than a law, and the code vocabulary grows by one stable prefix per failure family.

## Testing

`packages/client/runtime/tests/tool-outcome.client.spec.ts` pins the classifier: each stable code maps to `success`, `stopped`, `blocked`, or `error`, and unknown or uncoded failures stay `error`. `packages/client/ui-tool/tests/tool-row.client.spec.tsx` and `tool-row-styles.client.spec.ts` pin the shared row-state derivation through `toolOutcomeKind` for the generic row and its keyed views, `packages/client/ui-skill/tests/skill-row.client.spec.tsx` pins the same derivation and the `Error: `-envelope drop on blocked skill rows, and the trajectory `table`/`layout`/`conversation-definitions` client specs pin that only `error` renders the failure state, that a user or parent stop settles as `stopped`, and that a provider failure stays `error`. The real bash-abort row snapshot (`apps/web/tests/snapshots/bash-abort-row`) passes in both refresh and replay: Chat shows a stopped Bash row with its collapsed argument summary and one expanded durable abort output without a red marker, while Trajectory shows both stopped Bash rows and no failure marker. `packages/extensions/ui-cordis/tests/card-model.client.spec.ts` also pins the same classifier for Cordis keyed rows. `packages/core/tools/tests/tools.spec.ts` covers per-agent schema projection: `schemasFor(agent)` applies `projectSchema` with the exact live agent while `schemas(scope)` stays static and never invokes it. `packages/shell/tool-bash/tests/tools.spec.ts` and `integration.spec.ts` pin the escalation advertisement under a `'never'` policy or `danger-full-access` mode and the projected schema. `packages/sandbox/sandbox/tests/escalation.spec.ts` pins the `INVALID_ARGS` argument pairing, the `SANDBOX_ESCALATION_*` outcome mapping, and the redundant non-widening request (effective mode, no approval, no error — even with no approval service and no agent). `packages/interaction/user-approval/tests/approval.spec.ts` pins the `'never'` policy resolving every ask to `'blocked'`. `packages/guard/repeat-tool-reminder/tests/repeat-tool-reminder.spec.ts` pins the advisory reminders and the failure-aware tier at the second attempt. `packages/fs/tool-fs-search/tests/tools.spec.ts` and the integration suite pin the `globExcludeNodeModules` arm, the description adaptation, and the partial-result warnings. `packages/goal/tool-goal/tests/tool-goal.spec.ts` pins the integer revision (fractional → `INVALID_ARGS` before authority checks, integer-valued accepted), the omit-style error text, and the empty-filler acceptance.
